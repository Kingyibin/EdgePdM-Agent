## 1. 这个项目到底在干什么

工厂里的电机、泵、机器人关节会慢慢坏。**预测性维护**想在坏之前知道「大概还剩多久」。

我们**没有**工厂真实数据（保密、脏、不可公开复现），所以用 NASA 公开的 **C-MAPSS**：仿真航空发动机从健康跑到失效的多传感器时间序列。发动机只是**练习场**，方法可以迁到电机/关节。

三件事串起来：

1. **算法**：根据过去一段时间的传感器，预测剩余寿命 RUL。
2. **端侧**：把模型从 Python 变成 C++ 能跑的 ONNX，证明边缘设备也能推理。
3. **解释**：本地小 LLM 把「RUL=118、风险=预警」说成人话。**它不许改数字。**

不是手册 RAG，不是微调大模型，不是从零写推理引擎。

## 2. 必须先懂的基础知识

### 2.1 时间序列

一串按时间排列的数。这里每个发动机（unit）每个运行周期（cycle）有一行，上面有温度、压力、转速等传感器。

**泄漏（leakage）**：用了「未来才知道」的信息。如果把 100 台发动机的所有行随机打乱再切训练/测试，测试集里可能出现和训练集**同一台**后面的周期——模型等于偷看了这台机器怎么坏的。所以必须 **按 unit 切分**：某台要么在训练，要么在测试。

### 2.2 RUL

Remaining Useful Life：从**当前 cycle** 到**失效那一 cycle** 还剩多少周期。

训练数据跑到失效，所以 RUL = 该 unit 最大 cycle − 当前 cycle。  
测试数据被截断，官方另给 `RUL_FD001.txt`：每台测试机「截断时刻再过多少周期会坏」。

**capped RUL=125**：早期 RUL 很大时，传感器几乎没退化，硬学「还剩 300」没有稳定信号。把标签上限截成 125 是 C-MAPSS 论文里的常见设定，让模型集中学**快坏时**的模式。面试被问「为什么 125」：经验设定 + 与公开 pipeline 对齐，不是物理寿命。

### 2.3 滑动窗口

LSTM 要看一段历史。`window=30`：用最近 30 个 cycle 的 17 维特征，预测窗口**最后一拍**的 RUL。

代码：`src/sequence.py` 的 `build_windows`（训练：每个可满窗的终点都是一个样本）和 `last_window_per_unit`（测试：每台只用最后 30 拍；不够就前面重复第一行 padding）。

### 2.4 标准化

传感器量纲差几个数量级。`StandardScaler` **只在训练集 fit**，再 transform 验证/测试。如果把测试也拿去 fit，等于用测试分布调尺度，又是泄漏。

### 2.5 RMSE / MAE / NASA Score

- **MAE**：平均绝对误差，好懂，单位和 RUL 一样。
- **RMSE**：把大误差平方后再开方，对「错得很离谱」更敏感。
- **NASA Score**（越小越好）：非对称。预测得**太乐观**（以为还能跑很久，其实快坏了，`pred > true`）惩罚更重（分母 10）；预测得保守（`pred < true`）分母 13。代码：`src/metrics.py` `nasa_score`。

所以「RMSE 14.27、Score 324.6」是**同一组预测**的两种看法：一个看整体误差，一个看「晚报警有多糟」。

### 2.6 LSTM 一句话

循环网络：每一步把「当前传感器」和「上一步记忆」混在一起。适合「退化是慢慢积累的」。双向、三层、Attention 都可以试，但本项目正式交付是 **2 层、hidden 64、window 30**（`exp_20260722_lstm_fd001`）。更深不一定更好，数据只有 100 台训练机。

### 2.7 ONNX / ONNX Runtime

ONNX 是模型的「中间语言」。PyTorch 训练完导出 `.onnx`，C++ 的 ONNX Runtime 加载同一文件做前向计算。目的：边缘机不一定装 Python/PyTorch。

### 2.8 llama.cpp

把量化后的权重（GGUF）在 CPU 上跑小 LLM。本项目只用它**读 JSON 写建议**，相当于「模板扩写」，不是第二个预测器。

## 3. 数据长什么样（G1）

FD001：100 台训练（跑到坏）、100 台测试（中途截断）。

每行：`unit, cycle, 3 个工况, 21 个传感器`。很多传感器几乎是常数，正式特征用 **17 个有变化的**（见 `configs/default.yaml` / `src/features.py`）。

校验（`data/README.md`）：`train_FD001.txt` 20631 行；测试 13096 行；RUL 文件 100 行。下载走 Zenodo zip，因为 NASA 门户不好脚本化（T-002）。

## 4. 模型怎么比（G2–G3）

| 模型 | RMSE | MAE | Score | 角色 |
|------|------|-----|-------|------|
| Ridge | 20.84 | 16.34 | 1285 | 线性下限 |
| XGBoost | 17.48 | 12.29 | 929 | 强表格 baseline |
| LSTM | **14.27** | **10.48** | **324.6** | 正式交付 |

出处：`experiments/exp_20260722_* /metrics.json`。

**为什么 LSTM 能赢 XGB？** XGB 吃的是「当前 cycle 的手工滚动统计」；LSTM 吃 30 步轨迹，能看到斜率/加速度。不是「深度学习一定强」——window 太短或数据泄漏，LSTM 也会输。

**马拉松扫描**（`training_marathon.py`）：后来闲时把 window/hidden/layers/lr/seed 打乱真训。最优大约 RMSE 13.10（`r01_w30_h64_lr5e4`），但**没存权重、没重导 ONNX**。正式端侧仍是 14.27 那份 `lstm.pt`。同结构换 seed 可以从 ~13.4 晃到 ~15.3：说明你要能讲「不是只跑一次运气」。

## 5. C++ 端侧到底证明了什么（G4）

流程：`scripts/export_lstm_onnx.py` → `models/onnx/rul_lstm.onnx` → `cpp_inference/src/main.cpp`。

**诚实边界（ADR-006）**：C++ **不**做滚动均值、不 fit scaler。它读一张**已经缩放过**的 30×17 CSV，喂给 ORT。证明的是「推理引擎 + 延迟」，不是「特征工程已全部 C++ 化」。面试追问就直说：下一步才是把 mean/scale 写进 sidecar 在 C++ 里减除。

延迟：warmup 5 次丢掉，再 50 次取平均 **0.167 ms**，单线程。这是**单窗口、单样本、这台 Windows CPU** 的数，不是产线 1000 台并发。

对齐：同一窗口 Python ORT 118.4717，C++ 118.472。差在浮点打印，不是两套模型。

踩坑：没编译器（T-004 WinLibs）；ONNX dynamo 在 GBK 控制台炸（T-005 `dynamo=False`）；MinGW 不能链 MSVC 的 `onnxruntime.lib`（T-006 `gendef`+`dlltool`）。

## 6. LLM 解释（G5）

`agent/explain_client.py` 把 JSON（RUL、风险、异常传感器）塞进 prompt，打 `llama-server`。

**ADR-007**：LLM 不得改 RUL。0.5B 真的会把 RUL 说成「年」（T-008），示例故意留着瑕疵。换 1.5B 是质量问题，不是架构问题。

## 7. 决策为什么这样（压缩版）

| 决策 | 理由 | 不选的 |
|------|------|--------|
| 公开 C-MAPSS 而非厂内手册 | 可复现、可写数字、补 C++ 短板 | 手册 RAG（资料不够、和 CursorRAG 重复） |
| 先 XGB 再 LSTM | 没有 baseline 的深度学习是 magician | 一上来 Transformer |
| window=30 | 与常见 FD001 设定对齐，G3 一次跑通 | 扫描里 35/40 更好也不能静默改正式模型 |
| C++ 先吃预缩放 CSV | 先证明 ORT 链路 | 第一版就重写全部特征 |
| LLM 只解释 | 小模型预测 RUL 会胡编 | 让 LLM 当回归器 |
| 扫描不替换 14.27 | 没有权重 + 没有 C++ 复验 | 把 13.1 写进简历主数字 |

## 8. 刁钻追问（按层）

**数据**  
- 封盖复盘（2026-10-08，`docs/07_seal_review.md`）：剩余寿命不到 30 周期的 25 台 RMSE 约 4.4；60–90 那段最差。Score 的 44% 来自最差 5 台。验证 13.70 是留出机组的全部窗口。训练满窗里 30.1% 标签为 125。测试最短 31 周期，没有触发填充。预测低于 30 当作临期触发时，25 台里漏 5 台，都是贴着阈值（预测 30–34）。
- 测试集为什么没有完整 RUL 曲线？因为截断 + 单独标签文件，模拟「现在还没坏、但你要估计还剩多久」。  
- 21 个传感器为什么不用全？常数通道无信息，噪声。  
- FD002/004 有多种工况，FD001 是单工况——别说已经泛化工况。

**划分**  
- 为什么不用随机 8:2 行？泄漏，见 §2.1。  
- 验证集怎么来？按 unit 再划 20%，scaler 仍只 fit 训练 unit。

**指标**  
- RMSE 14.27 能发论文 SOTA 吗？不能。公开 LSTM/CNN 有更低的；我们的卖点是**同口径 baseline + 端侧链路**。  
- Score 为什么比 RMSE「好看这么多」相对 XGB？非对称惩罚让「少报大错」的树模型更惨。

**模型**  
- 为什么不用 Transformer？样本少、窗口短，过参数。  
- Dropout / MC Dropout：扫描里有覆盖率，正式 LSTM 实验 notes 以点估计为主；覆盖率 67% 说明**没校准到 95%**，别说已经有可靠不确定度。

**部署**  
- 0.17ms 算快吗？对 30×17 的小 LSTM，CPU 上这个量级正常；瓶颈若在特征工程，这个数不能代表端到端。  
- 动态 batch？当前程序一次一个窗口。  
- 量化 INT8？没做。

**LLM**  
- 为什么不 RAG 手册？项目非目标；解释层没有维修手册。  
- 为什么不让 LLM 看原始波形？上下文爆炸且会编。

**过程**  
- 全是 AI 写的吗？算法实验、C++ 链接、GGUF 404 是真跑出来的（T-001–T-009）。AI 帮你写文档和脚手架。会讲坑比会背 README 重要。
